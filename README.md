# ArmasVIP

**ArmasVIP 2.2.0** is a persistent VIP weapon ownership system for FiveM. It is designed for server owners who assign or sell a specific VIP weapon to a specific player while keeping ownership authoritative on the server and persistent in the database.

> **This repository contains documentation only.**  
> **The protected runtime resource is distributed through Cfx Asset Escrow.**

## What ArmasVIP is

ArmasVIP does not give every VIP player access to a global weapon catalog. The server owner or authorized staff assigns a concrete weapon to a concrete player. That assignment creates a persistent **grant**. The grant represents ownership of the VIP weapon independently from the temporary physical item stored in `ox_inventory`.

If the physical weapon disappears because of death, loss, restart, inventory state, or another supported circumstance, the grant remains. The owner can recover the weapon from the personal VIP Arsenal only after the server validates the grant and ownership.

## Features

- Persistent VIP weapon grants stored in SQL.
- Server-authoritative administration protected by FiveM ACE.
- Separate administrative panel and personal player Arsenal.
- One physical VIP instance per grant to reduce duplication abuse.
- VIP metadata associated with the grant and owner.
- Transfer protection integrated with `ox_inventory` for VIP instances only.
- Non-degrading VIP weapon durability without changing normal copies of the same weapon.
- Initial physical accessories that are not regenerated on later recovery.
- Persistent camo/tint unlocks validated server-side.
- Qbox, QBCore, ESX, and standalone identity support.
- `oxmysql`, `ox_lib`, and `ox_inventory` integration.
- Cfx Asset Escrow distribution model.

## Admin panel

Authorized staff use `/armasvip`. Administrative access is controlled by the ACE permission `armasvip.admin`.

```cfg
add_ace group.armasvip armasvip.admin allow
add_principal identifier.license:YOUR_LICENSE group.armasvip
```

The client UI is never treated as the authority. Sensitive operations are validated again on the server.

## Personal VIP Arsenal

Players use `/misarmasvip`. The personal Arsenal is separate from the administrative catalog. A player only sees VIP weapons backed by valid grants associated with that player's persistent identity.

## VIP instance vs normal weapon

VIP behavior belongs to the **specific VIP instance and grant**, not globally to a weapon name. A VIP `weapon_appistol` and a normal `weapon_appistol` may share the same base name, but only the instance carrying valid VIP metadata receives VIP behavior.

## Recovery and anti-duplication

Before creating or recovering a physical VIP instance, the server verifies ownership, active grant state and whether another valid instance associated with that grant already exists.

## Accessories

Accessories supplied with the initial assignment are physical components. They can be removed, changed or lost and are not regenerated by later weapon recovery.

## Camos and tints

Camo/tint unlocks are persistent grant data. The server validates that a requested cosmetic is unlocked for that grant before allowing it to be applied.

## Dependencies

Required: `oxmysql`, `ox_lib`, `ox_inventory`.

```cfg
ensure oxmysql
ensure ox_lib
ensure ox_inventory
ensure armasvip
```

Framework identity support: Qbox, QBCore, ESX and standalone fallback using Rockstar license.

## Security model

ArmasVIP is designed around server-side authority. UI visibility is not a security boundary. The server validates administrative ACE permission, identity, active grants, ownership, weapon/grant association, VIP metadata, instance state, cosmetic unlocks, grant status and client/NUI supplied values.

See [Security](docs/SECURITY.md) for the complete model.
